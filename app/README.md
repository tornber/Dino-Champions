# Dino Battle web (Next.js + Anchor)
1. After `anchor build`, copy `target/idl/dino_battle.json` from your Anchor project to `src/idl/dino_champions.json` (Anchor 0.30+, same version as `@coral-xyz/anchor`).
2. Copy `.env.example` to `.env.local` and configure `NEXT_PUBLIC_RPC`.
3. `npm install && npm run dev`
The dev and start scripts run `server.ts`, which serves Next.js and the Socket.IO racing server on the same port. Run only one instance for this app. If the server reports that the port is already in use, stop the other app instance before starting another.
When developing from WSL against this Windows-mounted checkout, load Linux Node from NVM before running npm: `source "$HOME/.nvm/nvm.sh"`. The `predev`, `prebuild`, and `prestart` hooks then install any missing Linux native packages from the existing lockfile directly alongside the Windows binaries in `node_modules`; they do not replace the Windows packages or modify the lockfile. This avoids the Windows/WSL esbuild and Next.js SWC platform mismatch. Prefer keeping the checkout and `node_modules` on the Linux filesystem for regular WSL development.
Run `initialize` once (deployer wallet) before creating competitions.
Before the game starts, the page attempts to clear this website origin's local/session storage, accessible cookies, IndexedDB databases, Cache Storage, and service-worker registrations. This can reset wallet auto-connect and other site preferences. Browser APIs cannot clear HttpOnly cookies or reliably enumerate/delete every cookie, and blocked databases or storage cause play to remain disabled with an error.
Each competition splits its scheduled play time evenly among three stages: Dino Run, multiplayer Rocket Race, then Flappy Bird. The Socket.IO server runs the race rounds, movement, and race points; rounds repeat until the racing stage ends. Scores from all stages are added to a competition-and-wallet-specific browser record preserved through the game's website-storage cleanup. At the end of the full competition, each player must approve one Phantom transaction to submit the combined total within the 60-second on-chain window. Scores restore after reload in the same browser; clearing browser data or changing devices can lose unsubmitted scores.
Rocket Race renders a real-time Three.js 3D circuit with procedural sports cars, a medium-distance chase camera with speed-responsive field of view, track scenery, lighting, separate steering and rolling pivots for visible front-wheel steering, and a live speed gauge driven by server-simulated km/h. Visual track progress maps one 600 m lap to one full circuit. Steering quickly changes lanes with mild throttle drag; the car's yaw and body roll reflect lateral motion, and corner speed limits ease in rather than snapping the car's speed down. Arrow keys steer in their indicated directions; A steers right and D steers left. Each round is three laps and the server simulates acceleration, braking, cornering, steering grip, drafting, contact, and finish order. Grids hold up to four racers; arrivals during a race are assigned to another grid. New grids have a 12-second formation countdown. Races can take around a minute and have a three-minute safety limit. WebGL/hardware acceleration is required; keyboard controls are supported. Multiplayer, timing, and scoring use Socket.IO.
The live race server is currently intended for local development. A deployed multiplayer competition needs a persistent, publicly reachable Socket.IO server configured on the same origin or a separately configured client/server URL, plus production-grade identity, anti-cheat, and score verification. Do not use client-submitted race scores for prize-bearing competitions without a trusted verifier: the on-chain program does not verify gameplay.
The game uses a best-effort DevTools heuristic for docked panels: if the browser window's outer/inner dimensions differ by more than 200 pixels, it stops play and stores a local lock for that competition and wallet. This can miss undocked/hidden inspector use, can trigger on unusual window layouts, and can be bypassed or cleared. The lock is only in that browser profile; it is not an on-chain or cross-browser ban and cannot undo a score already submitted. An attacker can still alter live JavaScript state or submit directly to the public program.
Players pay the network fee when they submit their final total. Result finalization and cancellation are manual actions with clear wallet transaction buttons; the page never initiates those transactions automatically. An expired competition with no entrants needs no cancellation transaction because there are no entry fees to refund. Creator-sponsored fees require a separate relayer/sponsorship design.
Build and upgrade the Anchor program, then copy its generated IDL into `src/idl/dino_champions.json` before using final-score submission; the website cannot add this instruction to an already-deployed program.
The frontend defaults to Solana Devnet through `NEXT_PUBLIC_RPC`. Set Phantom to Devnet as well. `anchor test` uses an isolated local validator by default; keep integration tests on localnet so they do not mutate shared public-chain state or consume devnet SOL. To deploy the program to Devnet, use `--provider.cluster devnet` explicitly after confirming the configured wallet and program deployment.

## Repair a deployed program

The checked-in Rust source and IDL target program `9hvmbZQU8scDSykiHEwV2j6t4GqJLwEEcm86KYzPUBNn`. If creating a competition reports `DeclaredProgramIdMismatch`, the deployed executable is stale; rebuilding the frontend or copying the IDL alone cannot fix it. Rebuild and upgrade the on-chain program on the intended cluster using the wallet that controls that cluster's upgrade authority:

```sh
anchor build
anchor upgrade --program-id 9hvmbZQU8scDSykiHEwV2j6t4GqJLwEEcm86KYzPUBNn --provider.cluster devnet target/deploy/dino_champions.so
```

The Devnet deployment's upgrade authority is `5ZarHPrqy7sFbWTHT2SFe6cSkkZQ8wRV77oH6TMxQgYL`; this does not establish the authority for other clusters. The upgrade command must be signed by the upgrade authority for the selected cluster. Never share its secret key. If you do not control that authority, deploy a new program under a key you control and update the program ID consistently in `Anchor.toml`, the Rust `declare_id!`, and both frontend IDL copies.
